# CourseMapper v0.8 Cost-Efficient Pipeline Plan

## Goal

Reduce generation cost without lowering course-package quality by changing the pipeline from artifact-first generation to a blueprint-first compiler workflow.

## Current Problem

The current pipeline asks the model to generate each deliverable independently:

1. Generate course map.
2. Generate each deliverable as full JSON/prose chunks.
3. Retry missing or weak chunks.
4. Run deterministic finalizer and localized retries.

This repeats course context, schemas, and instructional reasoning across many calls. For a 14-15 lesson course, the baseline is about 1 course-map call plus 25 deliverable chunk calls before repair and finalizer reserves. The highest output-token pressure comes from slide decks, quiz banks, assignments, study guides, and lesson plans.

## v0.8 Pipeline

The v0.8 pipeline introduces a canonical course blueprint and deterministic compilers:

1. Generate or accept the course map.
2. Build a compact course blueprint from the course map:
   - lesson outcomes
   - key concepts
   - activity patterns
   - assessment anchors
   - success criteria
   - student support needs
3. Compile stable deliverables from the blueprint:
   - syllabus
   - rubrics
   - assignment briefs
   - study guides
   - course FAQ
4. Keep LLM generation for high-creativity/high-variance deliverables:
   - lesson plans
   - slide decks
   - quiz bank
   - discussions
5. Keep the existing finalizer, readiness checks, export verification, and targeted retry behavior.

## Quality Rules

The compiler path must preserve or improve quality by making alignment structural:

- Every compiled item must reference a lesson number or assessment anchor.
- Assignment, rubric, syllabus, FAQ, and study-guide content must derive from the same blueprint fields.
- The existing validators and package finalizer remain active.
- Compiler output must use existing expanded deliverable shapes so current views, exporters, and editors keep working.
- If the compiler cannot produce a valid deliverable, the existing model-generation path remains available.

## Implementation Phases

### Phase 1: Hybrid Compiler

- Add deterministic blueprint builder.
- Add deterministic compilers for syllabus, rubrics, assignments, study guides, and course FAQ.
- Wire those features into `generateAll` so they complete without provider calls.
- Record logs that identify compiled deliverables and saved model work.
- Add tests validating coverage, shape, and validation compatibility.

### Phase 2: Model-Enriched Blueprint

- Add an optional single blueprint model call for richer assessment anchors and course throughlines.
- Fall back to deterministic blueprint when the call fails or cost control blocks it.
- Track blueprint spend separately in the API usage log.

### Phase 3: Atom Generation

- Replace full slide/quiz generation with compact content atoms:
  - quiz stems, answer keys, distractors, rationales
  - slide narratives, examples, speaker-note seeds
- Compile final slide and quiz structures deterministically from those atoms.

## Expected Cost Impact

Phase 1 removes several full deliverable-generation calls from the normal path. For a 14-15 lesson course, it can avoid around 10 chunk calls before retries, while also reducing repair risk because compiled deliverables have deterministic coverage.

Phase 2 and Phase 3 should reduce both calls and output-token volume further by using the model for planning, critique, and compact creative atoms rather than full artifact rendering.

## Non-Goals

- Do not remove the current full generation path.
- Do not lower required deliverable coverage.
- Do not skip readiness, validation, or export checks.
- Do not make provider-specific cost assumptions in core compiler logic.
