# External AI authoring: evaluation and implementation

Reviewed 2026-09-19 against `CourseMapper_External_AI_Design_v2.zip` and repository HEAD `6d4b3880eb01206354441bc94a00b3c2ddc22d5f`. The ZIP is a design proposal, not authority to publish, deploy, spend money, or accept its own claims of success. Its referenced baseline differs from the current repository.

## Evaluation and refinements

The central design is sound: external AI writes isolated drafts; a teacher previews and applies them; authored text remains authoritative through persistence and exports. Integrating only a tool endpoint would not satisfy it. The existing native deliverable shapes, editor updates, compact restores, cloud writes, finalizer, and exporters all needed attention.

Implemented decisions:

- Restricted copy/import tasks now target the existing permitted draft. The response envelope binds request/draft IDs, source/permission revisions, lesson contracts and a stable retry ID. Multi-lesson partial retries preserve successful submissions without duplication. Only permitted source text is copied. Unchanged passages may retain existing citations to unshared sources; rewritten passages cannot reuse them. Production browser verification covers a scoped rubric revision through import, apply, edit and project export.
- Browser fault injection verifies rollback on quota error and transaction abort, explicit storage-access denial, and recovery after commit completion is withheld from the UI. Recovery now restores the durable Undo action; guarded undo still rejects later teacher edits. These checks use real Chrome IndexedDB transactions, not physical disk exhaustion or an OS process crash.
- Teacher-only source replacement uses ownership and storage CAS, increments contract/grant revisions, and invalidates unapplied draft reviews. Stale references must be revised; new sources do not silently expand a limited grant. Pending application reservations block source changes, and applied records remain intact. Local browser checks verify removal/replacement and permission reset.
- Local attachment review supports explicit file selection, opt-in sharing, cancellation, redacted text preview, and text extraction through the existing document parsers. Source context and contracts carry extraction limitations; unparsed images/scans cannot claim readable excerpts. Original file bytes are not uploaded.
- One transport-independent authoring service and shared contracts. The page adapter exposes 13 tools; the remote MCP adapter exposes 14, including request creation. Neither exposes apply/approve/commit.
- Runtime schemas compile ahead of time. Production CSP does not need `unsafe-eval`.
- Real HTTP isolation tests exercise all 12 website routes and 14 MCP tools with two identities. Owner checks deny cross-account identifiers without mutation, and website/MCP credentials cannot be interchanged. Authorization headers require a Bearer scheme and accept its case-insensitive spelling.
- Website permissions use a document epoch and current request context. Registration is safe across StrictMode; old calls cannot commit after permission changes.
- Request ownership, scope, expiry, revocation, contract revisions, CAS, and durable idempotency receipts are enforced by the service, including Admin SDK paths. Teachers can narrow completed draft revision access to selected lessons, sources, and material types. The model cannot expand that grant; changes invalidate prior review and permission-bound contracts. Unselected lessons and sources are hidden, and ungranted authored fields remain fixed.
- Validation checks complete lesson-objective coverage, assessment/rubric objective alignment, globally unique concept definitions, and acyclic prerequisite links across lessons. These are structural checks, not subject-matter certification. Native projections preserve original authored bundles and teacher overrides. Worked examples, results, and teacher explanations appear in existing material renderers and exports. Student assignments exclude private answer text.
- Three-way review preserves current teacher edits and stops on conflicts. Arrays are atomic; reorder conflicts are deliberately not guessed away.
- Remote application intent commits to IndexedDB before the reservation request. Interrupted responses resume the same application ID; prepared intents cannot be treated as applied projects, and concurrent tabs cannot create competing intents for one account. The website can discard an intent only after the server records its cancellation; an existing reservation stays locked. Local application and recovery records commit transactionally before UI updates. Remote recovery uses account-specific pointers and the latest saved teacher edits; it preserves an already-open application and refuses to overwrite another course. Responses arriving after an account change are discarded. Conflicting receipt hashes are rejected, and the owner can acknowledge a saved application after revoking AI access. Later local saves reject stale tabs. Remote reservations never automatically unlock just because time passes; uncertain application requires receipt resolution.
- Authored projects use full IndexedDB snapshots and immutable, hashed cloud blocks with manifest CAS. Missing blocks fail explicitly; compact restore and finalizer cannot synthesize replacement prose.
- Export/readiness repair and automatic rubric coverage repair cannot rewrite authored material. The browser export check caught and fixed legacy replacement of assignment prose and 40/60 rubric weights.
- Lesson plan, assignment and rubric PDFs use readable field/content rows. A lazy self-hosted OFL font preserves covered Chinese and mathematical characters. Unsupported characters (including some subscripts and emoji) fail explicitly with a DOCX alternative; the approximately 19 MB font downloads only when needed.
- External mode blocks website model entry points. Selecting website generation is explicit.

Teacher-only requirement changes update the brief, learner profile, language, lesson count and duration. Old unapplied drafts remain in history as superseded and cannot be resumed, reviewed or applied; applied records remain unchanged. Changing requirements requires full request access and no unresolved application. The production browser verified a revised brief, two lessons and a new duration, rejected the old draft, and copied the revised task. HTTP tests verify ownership and stale-write rejection.

Error responses expose detailed messages only for deliberate AuthoringError instances. Coded storage/SDK errors and malformed thrown values return a generic internal error without their messages, paths or details. Tool and authenticated HTTP tests inject private diagnostics and verify they are absent. Authoring server logs currently contain startup status and cleanup counts only; this does not certify external infrastructure logging.

Source reads carry an untrusted-reference-data marker and generation contracts explicitly separate source text from instructions and authorization. A service test supplies source instructions to read unshared content, change ownership, create a draft outside a narrow grant and apply a course; all requested privilege changes fail without mutation. The production browser also verifies script/event-handler text in a source preview does not execute. This verifies host enforcement, not an external model’s resistance to all prompt injection.

## Live deployment discovery

The user selected **edutool.dev**. Public HTTP headers and `.github/workflows/deploy.yml` confirm GitHub Pages hosting. `src/lib/firebase.js` and `AuthContext.jsx` configure Firebase Authentication with Google sign-in, project `coursemapper-a92c4` by default. Local configuration contains Firebase settings but no external OAuth issuer.

On 2026-09-19, `https://edutool.dev/.well-known/oauth-authorization-server`, `/.well-known/openid-configuration`, and `/.well-known/oauth-protected-resource` all returned HTTP 404 HTML. There is no discoverable external authorization service on this hostname. This does not prove the owner has no unrelated identity-provider account.

GitHub Pages cannot run the Express MCP service. Recommended deployment shape: retain the existing website; host the exchange on Cloud Run behind a verified API subdomain; use a maintained OAuth provider (for example Auth0) for authorization-code + PKCE and link its verified subject to an existing Firebase UID. Do not identify accounts merely by matching an unverified email. An alternate same-origin proxy requires deliberate hosting/routing changes. These are proposals, not resources already provisioned.
