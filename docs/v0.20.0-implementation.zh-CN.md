## 2. 第一段 schema 决策

保留外层 `COURSE_GRAPH_VERSION = 1`，新增可选的 `teachingProgram.version = 1`。没有教学程序的旧图仍可读取。后续增加操作和评分协议时单独版本化，不能把本轮版本号误解为整个 v0.20.0 schema 已冻结。

当前程序包含：

- `objectives`：任务需要学生展示的具体表现，稳定 ID 和文本。
- `sources`：带稳定 ID 的输入陈述；旧来源标为 `legacy-task-input`，不追认其事实真实性。
- `tasks`：通过 `objectiveRef`、`inputs[].sourceRef` 引用目标与来源，保留任务 ID、原输入 ID、课次绑定、时间、作用域和未知的教师字段。
- `revision`：对规范化 JSON 计算摘要，用于检测变动和不完整保存；不是事实认证或教师审批。

任务层表现与旧课程总体 outcomes 的正式对齐关系仍待 M2 实现。首轮存储迁移仍通过旧 solver 派生推理和评分；后续首个操作的绑定与评分权重已写入任务，见第 8 节。所有教学实体的统一尚未完成。

没有根据文本相同自动合并来源。两个独立案例即使陈述相同，也保留各自身份。显式共享引用可表达共同来源；不同任务对同一引用提出相互矛盾的更新时拒绝静默选择其中一个。

`teachingTaskSources` 继续存在于材料快照和 map 的兼容视图中；只要程序存在，读取时以程序为准。新的图不在 `course.meta` 另存这份 ledger。旧文件中用户自定义的来源、输入和任务字段需往返保留。

### 8.1 题目、答案、评分与对照作答一起改

原评分的 Developing 档只举了错误结论，没有合理覆盖“结论正确但缺少解释”。新描述区分有效范围的解释、只有结论的回答和“新记录证明旧记录从来错误”的误解。

题目、参考解答和最高档都明确要求提出一份能够补足日期缺口的具体佐证，避免只在评分中偷偷增加要求。参考解答把拟寻找的记录与已经取得的事实分开，也接受其他相关佐证。

每个该类核心任务现在产生四种检查用回答：完整推理、正确结论但推理不足、典型误解、合理的替代表达。记录按评分要求关联的判断、理由和精确作答摘录。Rubrics 与 Assignment Briefs 的现有教师参考折叠区展示这些内容；Word 的 rubric 教师参考也包含四类示例。它们是作者构造的检查材料，不是学生数据，也未取得独立评分信度证据。

新要求不能把旧生成文字误判成教师覆盖。为此从真实 v0.19.2 发布工程提取 Study Guides 回归夹具，并保留仅用于三方合并的历史呈现基线；接受修改后写入新的明确操作。这一兼容基线不参与新的内容生产。

## 13. 一般表现要求、稳定材料身份与真实编辑往返

本阶段解决“改任务动作后，旧参考、评分或练习仍留在材料里”的问题。它是 M3 的局部交付，不能替代 M0/M2 的真实模型与操作能力、M4 的完整课程质量或 M5 的独立验收。

### 13.1 同一操作合同中的表现要求

在已有 `operationPlan` 内增加版本 2；外层教学程序和 CourseGraph 继续沿用已有权威入口，没有新建第二套任务库。`teachingPerformanceRequirements.js` 验证并投影每项要求的稳定身份、权重、学生动作、参考作答、推理步骤、四个评分档位、错误反馈、指导问题、构造的对照回答及独立案例任务。独立案例拥有单独的来源记录与来源类别。

要求可以增删，不再局限于某个操作预设的三个评分项目。删除要求时共同重建题目、答案、评分、错误分析、指导练习、独立练习和相关材料；新增要求获得新身份。来源或目标改变后，旧的教师参考必须重新核对，不能因为算术仍能求解就自动确认整段解释。

程序检查字段、身份、引用、权重、来源版本及明确的计算边界；教师编写的开放解释仍记录为“教师审阅内容”，不标成机器已证明。四类构造回答保留对应文字位置，用于审查 rubric；它们不是学生数据，也不证明真实评分区分度。减少评分项目不改变底层事实边界，例如取消“总体限制”评分后，未观察总体的比例仍然未知。

旧版合同继续兼容。版本 1 不接受伪装成旧权重的新版内容，模型提案也不能借兼容规则获得教师确认。

### 13.2 原界面中的审阅与实际负担

原有 `Review sources and scoring` 入口中增加要求编辑。每项要求展开后可以编辑任务、参考、评分和练习；预览列出受影响材料，确认后才写入同一事务，继续使用已有冲突保留和历史恢复。

这里仍有产品缺口：从旧合同开始编写新要求集合，目前得到空白草稿；教师要填写并核对一整套内容，尚未有 Scion 预填或可靠的自然语言修改提案。因此，本阶段证明了编译和修订能力，尚未证明它比教师手工编写更省时间。目标与课程 outcomes 的正式对齐也仍未完成。

### 13.3 实际材料审计暴露的缺陷与修复

1. **幻灯片内容身份依赖位置。** 删除一个要求后，其他要求可能占用原来的 slide role。新版示范、错误分析和指导问题改用要求身份；教师备注不会因为前项被删除而迁移到别的要求。
2. **空活动字段造成假冲突。** 旧编译新增内容页省略 `activity`，重放时写入 `null`，删除未编辑页因此被误判为教师修改。现在只对有生成身份的内容页识别这两种空值等价；真实备注和活动仍保留并产生必要冲突。
3. **题库固定槽位留下已删除要求。** 原来只覆盖前几个题目，余下题目的旧任务与参考继续存在。新版按练习身份重建受管题目，保留匹配题目的身份及分值、非受管教师题和真实覆盖，移除过时生成题；重新计算实际题数与总分。
4. **少分值、多要求可能分配出负数。** 新版 rubric 用整数分配与稳定余数排序处理，确保总分准确且分项非负；旧版兼容路径不变。

题库新增练习默认 1 分，并在分值说明中明确提示审阅；已有题分值保留。这还不是最终测验设计：题量配置、各类题的认知要求、同一题库中主作答和 checkpoint 重复提示的用途需要在 M4 继续审查。不能把“数量与分值一致”写成“测验已适合课堂”。

## 14. 新任务创建、本地来源提案与实际恢复

### 14.1 在原材料界面创建教学任务

### 14.2 从来源提案到可核对任务

`scionTeachingProposal.js` 只请求两种操作需要的来源角色与精确片段，使用应用已有的本地运行时。输入最多 8 条、合计 6,000 字符，输出预算 1,024 tokens；一次提案最多加一次结构/摘录修复。无效输入不加载模型，重复任务不并行推理，支持取消。未知角色留空，截断不作为完整提案接受；JSON 格式正确仍需前提检查与教师语义核对。

真实开发输入为沿海巢箱的 7/25 记录、未调查内陆巢箱和全部巢箱的总体边界。首次接收器拒绝了模型额外附上的准确整条原文，修复调用又产生坏 JSON。第二版仅放宽可逐字核实的完整 record 引文；缩短或虚构引文仍拒绝。若修复更差，保留较完整的一次提案及所有原始记录，不拼接不同回答冒充一次成功。

### 14.3 实际检查发现的创建与后续编辑缺陷

### 20.2 修复错误准入，而非放宽检查

原 assessor 在片段只有一个匹配时，忽略显式 `occurrence: 1`，自动改用唯一的序号 0。英文具名分组回复的十一处片段全部这样写，原收据因此记录了零问题；这是一项程序误判，不能据此声称模型成功。现在 assessor、建议合并、草稿预览均保留并验证显式序号；仅在未给序号且唯一匹配时补 0。实际旧收据按新校验重放会报告十一处定位问题，原字节不改写。

同时检查处理片段与另一条件片段是否重叠。把“某种墨水在某温度下测试”整个句子选作处理，再把其中温度选作另一条件，会被拒绝；这条检查在模型提案和正式操作合同中共用。它不能识别所有语义错误，例如把不重叠的结果句误当条件，仍须教师审阅。

分组提案的一处片段类型错误不再抹掉其他有效摘录。错误字段保持空缺，其他摘录仅作为建议；未知字段、伪造确认、错误来源、非原文引用、缺失前提仍不能成为已确认任务。修复请求说明具体字段、匹配数与零起点序号。原比例和记录修订协议保留。
