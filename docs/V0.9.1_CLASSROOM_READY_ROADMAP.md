# V0.9.1 Program — Classroom-Ready

One roadmap for everything between today's output and materials a university instructor ships under their own name. Consolidates the previously sketched v0.9.1 → v0.10.3 stages into a single program with five phases. The governing instrument is **[CLASSROOM_READY_RUBRIC.md](CLASSROOM_READY_RUBRIC.md)** (CCR v1.0): every phase exits only when the standing judge's scorecard shows the phase's target criteria at ≥3. Current baseline verdict: **DEVELOPING** — blocked on essential criteria D2.1, D2.2, D3.1, D3.2 (assessments test course process, not the discipline; key terms are circular).

Program north star, restated from the rubric: a pilot instructor hands the Lesson 1 packet to students with zero corrections for substance, voice, or facts — and the unconfirmed-items list is empty because they confirmed each item, not because we hid it.

## Phase 1 — Subject-Matter Enrichment I: assessments & key terms (target: 1–2 weeks)

The architectural centerpiece: a budgeted model pass writes disciplinary content _inside_ compiler-owned frames. The compiler keeps structure, alignment metadata, numbering, policies, trust records; enrichment supplies what a deterministic program cannot — knowledge.

**1.1 Enrichment engine** (`src/lib/blueprintEnrichment.js`, new):

- Input contract per lesson: course identity, lesson objectives + Bloom's plan, topics, the course map's own readings, assessment plan (type/count/difficulty per item), instructor/institution profile, voice notes.
- Output contracts (strict JSON, validated like existing generation): per-surface payloads merged into the blueprint as `enrichment.*` fields the compilers consume; every enriched field stamped with `enrichmentSource` provenance so `explain_design` and the trust strip can attribute it.
- Grounding rule (hard): enrichment may reference only the course map's readings/topics; introducing a new source requires the `search_research` path with verification metadata. Fabricated-citation policy applies; violations are blockers in validation, not warnings.
- Budget: chunked, ~1–2 calls/lesson on the configured mini model (≈$0.50–2/course); integrated with `apiCallBudget` cost plans + soft/hard limits; `blueprintEnrichmentRequested` flag becomes real and defaults on when an API key is present, with the compiled-only path kept as the no-key/offline fallback.

**1.2 Surface: quiz items** (CCR D2.1, D2.2):

- The compiler's per-item plan (type, Bloom's, difficulty, objective) becomes the enrichment order; the model returns stem + key + 3 distractors _with a stated misconception rationale per distractor_ + explanation + scoring guidance.
- Deterministic post-validation: Haladyna-derived lint (stem completeness, option homogeneity by length/grammar, no all/none-of-the-above, no clang overlap with key, single key), meta-content detector = 0, answer-key rotation preserved.

**1.3 Surface: study-guide key terms** (CCR D3.1):

- Terms selected from objectives/topics; model returns discipline definition + concrete example + common misconception; circularity lint (term must not be defined by the lesson title or its own words).

**1.4 Gates extended:** gold matrix and the 34-course sweep gain an enrichment-on profile (recorded fixtures, no live calls in CI); copy-variety, content-quality, rendered-text gates all bind on enriched output; red-team scenarios assert the grounding rule.

**Exit:** judge scores a regenerated two-course sample: **D2.1, D2.2, D3.1 ≥ 3**; spot-verification of content claims (D3.2) shows no factual errors in sample; meta-content count on quiz/key-term surfaces ≈ 0.

## Phase 2 — Enrichment II + truth & localization (target: 1–2 weeks)

**2.1 Surface: slide content** (CCR D4.1): assertion titles + evidence-bearing bullets (claims, numbers, examples) + explanatory speaker notes, within compiler deck shapes; Mayer lint (≤4 bullets, no meta-scaffolding nouns on student surfaces).

**2.2 Surface: discussion prompts** (CCR D3.4): a genuinely debatable disciplinary question with the tension named and 2+ defensible positions sketched in facilitation notes.

**2.3 Surface: assignment task cores** (CCR D3.4): the actual case/dataset/text and concrete parameters (length, data source, deliverable form) inside the existing brief frame; for lab/data courses, ties into Required Assets manifests.

**2.4 Localization interview** (CCR D6.5, D5.3): TA-agent guided flow (extends `professorProfile`/institution profile) collecting the facts only the instructor knows — term dates, meeting pattern, instructor identity/contact, LMS name, policy links — written through every artifact; placeholder scan goes to 0 for a completed interview.

**2.5 Assumption ledger → pre-export checklist** (CCR D3.3): the compiler's existing per-lesson assumptions/local-review actions surface as one checkable list in `ExportSidePanel` ("12 items need your eyes"), deep-linked via the shared-focus anchors; export allowed, state honest. Confirmations recorded in the course journal.

**2.6 Source verification:** readings proposed by enrichment run through `search_research`; verified → citation metadata; unverifiable → flagged in the ledger.

**Exit:** judge scores **D3.3, D3.4, D4.1 ≥ 3; D6.5 = 4 on a localized package**; trace_objective shows 0 unassessed objectives on samples (D1.2 ≥ 3).

## Phase 3 — Visual craft (target: ~1 week)

**3.1 DOCX themes** (CCR D6.2): 2–3 designed themes (typography scale, accent palette, spacing rhythm) in a theme module consumed by `docxExporter`; cover page + TOC for multi-lesson exports; institution name/logo slot from the profile.

**3.2 Deck redesign** (CCR D4.1, D6.2, D6.4): variable deck length driven by lesson content (retire the fixed 12-slide shape — the single most "compiled-looking" survivor); native charts/diagrams rendered from course data where the visual plan calls for them; `generate_slide_images` for the rest; density/hierarchy layout pass.

**3.3 Accessibility pass** (CCR D5.1): alt text everywhere, table headers, contrast check on themes, no color-only cues — verified by an automated structure scan added to export verification.

**Exit:** judge runs the blind side-by-side (D6.4): generated syllabus + one deck not reliably identifiable next to strong instructor originals; **D5.1, D6.2 ≥ 3**.

## Phase 4 — External proof (target: calendar-dependent)

**4.1 Pilot:** 2–3 real instructors (NYU network), their actual courses, full packages at proof scopes (5/8/14 lessons), reviewed against the CCR.
**4.2 Evidence loop:** their accepted/rejected edits feed the voice profile and edit-pattern memory; substantive corrections on D1–D3 surfaces become Phase-1/2 regression fixtures.
**4.3 Finish line:** the repo's expert-review audit (currently `internal-provisional-only, 1/12`) flips to external-proof complete for the shipped version — its requirements already match CCR D7 (≥2 reviewers, ≥2 modalities, proof scopes, concrete edit-history evidence, current version).

**Exit:** CCR verdict **CLASSROOM-READY** — all ★ ≥ 3 including D7, weighted total ≥ 85%. This verdict is issued by the rubric, not by us.

## Standing quality governance

- **Judge cadence:** CCR scorecard at every phase exit + any compiler/enrichment/exporter release; scorecards in `verification-output/classroom-ready-scorecards/<version>/`; verdict in release notes.
- **Floors stay automated:** all v0.8.61 gates (gold 40/40, copy-variety, content checks, rendered repetition, bundle budgets) remain CI-binding; the rubric judges above the floors, never instead of them.
- **Cost ceiling:** enrichment ≤ $2/course default budget, visible in cost plans and receipts; compiled-only path remains the documented offline fallback at DEVELOPING quality.
- **Honest trust surface:** every enriched field attributable (`enrichmentSource`), every unconfirmed local fact visible in the checklist until the instructor clears it.
