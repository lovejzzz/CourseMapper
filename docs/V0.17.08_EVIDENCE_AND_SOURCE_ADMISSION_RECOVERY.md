# V0.17.08 Evidence and Source-Admission Recovery

## Goal

Restore a release that passes on a clean checkout, make every promoted proof tamper-evident, and stop broad Python-package search results from becoming lesson evidence merely because they mention Python.

## Observed failure

The v0.17.07 push failed Fast verification because `CURRENT_RELEASE.proof.browser` named a local directory under ignored `verification-output/`. Local audits passed only because that directory existed in the authoring workspace. GitHub could not reproduce the claimed proof, so deployment correctly skipped and production remained on v0.17.06.

A fresh production package also showed that valid URLs and licenses are not sufficient semantic evidence. PyGMT, XSO, molecule archives, and unrelated scientific pipelines were attached to a beginner Python public-policy course, then amplified across visually polished artifacts.

## Lane 1 — Reproducible release proof

- Current benchmark and browser proof entries are structured records containing `path`, `sha256`, and `bytes`.
- The release-history audit reads the artifact, verifies its byte count and SHA-256, and asks Git whether the path is tracked.
- A local ignored path, missing file, stale hash, unsafe path, or tampered artifact now fails before a release claim can pass.
- The tracked browser receipt explicitly distinguishes predeployment runtime and regression evidence from a live course-quality result.

## Lane 2 — Falsifiable benchmark evidence

- Every required arm artifact must be an on-disk `{path, sha256, bytes}` record.
- Every compared metric must be finite; missing values cannot escape through JavaScript `NaN` comparisons.
- Evidence must include a blinded judge identity, a substantive attestation, and one valid randomized arm order for every frozen case.
- Duplicate, unexpected, sparse, missing, and tampered evidence fails closed.

## Lane 3 — Source-to-claim admission

- Computer-science retrieval now requires the source to match the exact recognized lesson topic rather than accepting the generic words “Python” or “programming.”
- The real PyGMT, XSO, and Mars-archive contamination families are regression fixtures.
- A source dependency is `resolved` only when a trusted row contains a semantic support receipt binding source ID, locator, quotation, authored claim, and rendered artifact location. URL-only or extraction-only rows remain `review-required`.

## Lane 4 — CI and output-texture recovery

- Automated-readiness fixtures now freeze the honest extraction-only result: source extraction receipts retain traceability diagnostics but receive no semantic-grounding credit.
- The former “source-rich positive control” is named as an extraction-only control so the suite cannot imply evidence support that the evaluator deliberately refuses to award.
- The repeated “Prepare or submit” closing-slide frame was replaced with a concept-and-evidence action tied to the lesson artifact.
- Cross-package post-repair checkpoints were advanced only after both panels improved every aggregate texture measure, added no universal high-salience cluster, grew no existing cluster, and retained over 92% causal compiler-frame provenance in the gold panel.

## Verification

- Focused adversarial tests cover exact tracked artifacts, untracked paths, byte/hash tampering, sparse benchmark metrics, truthy artifact placeholders, incomplete judging, Python-package bycatch, and incomplete source-to-rendered-claim chains.
- The standard format, lint, unit, build, bundle, release-history, clean-checkout, CI, deployment, and live-version checks remain required before the release is described as shipped.

## Release Boundary

V0.17.08 is a release-integrity and semantic-admission recovery. It does not claim that the strict five-course comparison has run, that Gemma is or is not the binding model limit, that v0.17.08 has passed external instructor review, or that the generated curriculum is a classroom-quality checkpoint. A deployed same-input ALGI/Scion/hybrid vertical slice remains the next causal experiment.
