# V0.15.132 Progress Log Bounds Roadmap

## Goal

Keep the generation workspace responsive during long provider runs by stopping
the progress details panel from mounting unbounded event history.

## Evidence

- Fresh deployed audit blocker:
  `verification-output/edutool-audit-loop/20260629T152606Z-v015130-fresh-blocker`
- Course: User Experience Design Studio
- App version: v0.15.130
- Run id observed before browser-control capture hung: `run-1782745776255`
- Runtime blocker: opening generation progress details during enrichment made
  Chrome show a `Page Unresponsive` dialog before ZIP/log capture completed.
- Visible state before the dialog: `Enriching lessons 1-12`,
  `Deliverables 0/9`, `1 material ready`, and disabled ZIP export.

## Diagnosis

The ProgressPanel activity log merged deliverable-generation events and
cascade-sync events, auto-opened while deliverables were actively generating,
and rendered every merged entry into the DOM. The scroll container limited what
was visible, but it did not limit what React mounted.

That is risky during provider runs because enrichment and compilation can append
many status events while the rest of the workspace is also streaming and saving.

## Lane

1. Keep long provider-run logs opt-in
   - Do not auto-expand the activity log merely because deliverable generation
     is active.
   - Preserve the count so the instructor can see activity exists.

2. Bound the expanded live panel
   - Memoize merged deliverable and sync activity entries.
   - Render a latest-event tail instead of every historical event.
   - Show an explicit count when older entries are hidden.

3. Preserve useful sync visibility
   - Keep cascade-sync logs auto-opening because they explain recent user edits.
   - Prove the sync behavior separately from long provider logs.

## Fix

V0.15.132 keeps the activity evidence but bounds the live UI cost:

1. Provider-generation activity logs stay collapsed by default during active
   deliverable generation.
2. User-triggered sync logs still auto-open because they are short and explain
   background edits after the user changes content.
3. Merged activity entries are memoized so repeated renders do not rebuild and
   sort the same arrays unless the logs change.
4. Expanded activity logs render only the latest 80 events and show an explicit
   `Showing latest N of M events` note when older events are hidden.
5. Focused happy-dom regressions prove the long provider log stays collapsed,
   the expanded log is bounded, and sync auto-open still works.

## Release Boundary

- This release fixes a runtime/UI blocker that prevented fresh ZIP/log proof.
- This release does not claim provider quality improved by itself.
- This release does not weaken source, export, report, digest, texture, or
  quality-grader standards.
