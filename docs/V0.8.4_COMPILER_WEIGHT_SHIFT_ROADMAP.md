# v0.8.4 Compiler Weight Shift Roadmap

## North Star

An instructor can open or restore a project, even with no working provider key, and still trust CourseMapper to regenerate, audit, repair, and explain course-package artifacts because the course truth lives in a lean source-grounded blueprint and repeatable artifact work lives in deterministic compiler/finalizer code.

## Release Claim

v0.8.4 is not a feature-expansion release. It is an architecture hardening release:

1. The blueprint becomes smaller and stricter.
2. The compiler becomes more responsible for artifact assembly, receipts, review surfaces, repairs, and stale regeneration.
3. Model calls are reserved for source interpretation, compact enrichment, unknown custom structures, image generation, and cases where deterministic code cannot safely infer the missing semantics.

## Core Architecture Decision

Split the current single heavy blueprint contract into two contracts:

1. `BlueprintSemanticContract`
   - Gates whether the source-grounded course truth is sufficient to compile.
   - Checks only minimum semantic atoms and safety boundaries.

2. `CompilerOutputContract`
   - Gates whether the compiler/finalizer produced complete, coherent, reviewable, export-safe artifacts.
   - Checks receipts, repair summaries, package coherence, dry-run support, review actions, and no proof-language leakage.

The current `validateCourseBlueprintContract` can remain as a compatibility wrapper during migration, but the release direction is clear: compilation should depend on semantic sufficiency, not on prebuilt receipt/report structures stored inside the blueprint.

## Minimum Blueprint

The blueprint must keep only source-grounded facts, compact semantic interpretations, and safety boundaries.

### Course Identity

- Course name.
- Term/semester when source-provided.
- Selected lesson scope.
- Ordered lesson count.
- Original source coverage/provenance.

### Course Lens

- Primary modality or course pattern: seminar, lab, studio, clinical, online, policy, language, data, etc.
- Learner role: researcher, designer, analyst, clinician, teacher candidate, communicator, etc.
- Evidence noun and decision noun used by the compiler.
- Compact enrichment atoms only when accepted: signature terms, lesson phrases, teaching moves, modality/lens cues.

### Lesson Atoms

Each lesson needs:

- Stable id, lesson number, and title.
- Objectives/outcomes.
- Key concepts and topic context.
- Readings/resources/source materials.
- Activity pattern or learning task.
- Expected student artifact.
- Success criteria.
- Bloom/cognitive demand signal.
- Source confidence, source anchors, source evidence trace, missing signals, and conflicts.
- Explicit local-review flags.

### Assessment Atoms

Each assessment needs:

- Stable id and title.
- Linked lesson number(s).
- Artifact being assessed.
- Source-provided weights/dates if present.
- Objectives assessed.
- Source-provided criteria if present.
- Whether weights, criteria, dates, or policies were source-provided or compiler-distributed drafts.
- Review-required reason when any assessment field is inferred.

### Safety Boundary

The blueprint must preserve:

- Approved source cues.
- No-invented-source policy.
- Citation/source-use expectations.
- Official facts that require instructor confirmation.
- Safety, clinical, accessibility, privacy, copyright, or institution-policy review flags.
- Ambiguity/refusal reasons when a requested artifact does not exist or cannot be source-grounded.

## Move To Compiler

These should become compiler/finalizer outputs, not required blueprint fields:

- `blueprintReviewSurface`
- `blueprintAssumptionLedger`
- `packageCoherenceMatrix`
- `compilerDecisionMatrix`
- `classroomDryRunPlan`
- `classroomEvidenceLoopPlan`
- `instructorFeedbackLoadPlan`
- aggregate `courseWorkload` summaries
- full `assessmentArchitecture` rows
- full `masteryEvidenceMap`, `evidenceResponseMap`, and `objectiveEvidenceMap`
- long `classSessionPlan` segment lists
- default `modelContrast`, `readinessSupport`, `prerequisitePlan`, `instructionalRationale`, `accessibilityPlan`, `feedbackCycle`, `learningTransferPlan`, and `teachingIntent` prose
- rubric performance-band prose, calibration prose, anchor-example prose, quiz rationale wording, discussion facilitation wording, slide-note phrasing, FAQ category wording, and study-guide question wording

The compiler may still derive and emit all of those. They just should not be required as prebuilt blueprint storage.

## Do Not Move To Compiler

The compiler must not invent or silently smooth over:

- Official dates.
- Official grading weights.
- Institution policy.
- Copyrighted readings or source details.
- Clinical, safety, legal, privacy, or accommodation requirements.
- Local examples the instructor has not provided.
- Novel custom deliverable structures with no safe deterministic pattern.
- Missing deliverables. The agent/compiler must refuse or explain instead of creating ghost rubrics, assignments, slides, quizzes, FAQs, or custom artifacts.

## Migration Plan

### Phase 0: Custom Family Compiler Expansion

Status: implemented in v0.8.4.

Implemented first:

- Feedback forms.
- Project milestone checklists.
- Lab reports.
- Case briefs.
- Policy memo checkpoints.
- Observation checklists.
- Participation/self-assessments.
- Capstone progress reports.
- Problem-set worksheets.

Rules:

- Compile only when the custom definition asks for one item per lesson/week.
- Keep whole-course, broad, unknown, or novel custom requests on the model path.
- Keep exports free of internal compiler proof metadata.

Verification:

- `src/lib/__tests__/courseBlueprintCompiler.test.js`
- `src/lib/__tests__/courseBlueprintCostComparison.test.js`

### Phase 1: Add The Lean Semantic Contract

Status: implemented in v0.8.4.

Goal: introduce `validateBlueprintSemanticContract` without breaking current audits.

Implementation slices:

1. Add a new semantic contract function that checks only minimum blueprint atoms.
2. Add a `semanticContract` field to built blueprints.
3. Keep `compilerContract` temporarily as the old heavy compatibility gate.
4. Add a test fixture that strips derived review surfaces from the blueprint and proves semantic validation still passes.
5. Add negative tests for missing lessons, missing objectives, missing source anchors, missing assessment anchors, and missing review boundaries.

Definition of done:

- A minimal semantic blueprint can be validated without `blueprintReviewSurface`, `classroomDryRunPlan`, `classroomEvidenceLoopPlan`, `instructorFeedbackLoadPlan`, `packageCoherenceMatrix`, or `blueprintAssumptionLedger`.
- Existing full contract still passes during the transition.
- `validateBlueprintSemanticContract` now gates compilation, while `validateCourseBlueprintContract` remains as the strict compatibility audit.

### Phase 2: Compiler-Owned Proof Bundle

Status: implemented in v0.8.4.

Goal: move receipt/report surfaces from blueprint storage into compiler/finalizer output.

Implementation slices:

1. Add `buildCompilerProofBundle({ blueprint, compiledDeliverables, selectedFeatures })`.
2. Move package coherence into the proof bundle.
3. Move assumption ledger rendering into the proof bundle.
4. Move blueprint review surface rendering into the proof bundle.
5. Move classroom dry-run, implementation evidence-loop, and feedback-load rows into the lesson-plan compiler or proof bundle.
6. Update syllabus receipts to read compact proof bundle data instead of requiring those structures on the raw blueprint.

Definition of done:

- Compiled packages still show trust evidence.
- The raw blueprint no longer has to carry full proof/report surfaces to compile.
- Receipts still show compiled/model-generated counts, repairs, skipped actions, failed actions, verification, and review requirements.
- `buildCompilerProofBundle` now derives proof surfaces for lean/restored blueprints, and `validateCompilerOutputContract` verifies selected compiled features, lesson coverage, proof status, and read-back receipt evidence.

### Phase 3: Assessment Compiler Extraction

Status: foundation implemented in v0.8.4; source-exact assessment policy remains the next hardening target.

Goal: keep assessment anchors in the blueprint, but generate assessment wording and scoring support in the compiler.

Implementation slices:

1. Keep source-provided assessment title, artifact, objectives, weights, dates, and criteria in the blueprint.
2. Move criterion weight planning into compiler policy unless source-provided.
3. Move rubric performance bands fully into `compileRubrics`.
4. Move calibration plan prose into compiler-owned rubric/assignment support.
5. Move anchor example prose into compiler-owned rubric/lesson-plan support.
6. Preserve review flags whenever weights, criteria, or dates are compiler-distributed drafts.

Definition of done:

- Source-provided assessment facts are preserved exactly.
- Draft compiler-distributed weights are visibly marked for instructor confirmation.
- Rubrics and assignments still pass validation and quality gates.
- The compiler preparation path can rebuild sparse assessment anchors from semantic lesson atoms when restored blueprints do not carry full assessment rows.

### Phase 4: Lesson Routine Extraction

Status: foundation implemented in v0.8.4; deeper blueprint-size reduction remains an audit migration target.

Goal: keep lesson atoms in the blueprint and derive teaching routines at compile time.

Implementation slices:

1. Replace stored long class-session plans with compact lesson timing/workload atoms.
2. Derive lesson-plan outlines in `compileLessonPlans`.
3. Derive default prerequisite, readiness, feedback, transfer, accessibility, and teaching-intent prose from compiler templates.
4. Keep explicit source-provided constraints and review flags in the blueprint.
5. Add tests proving compile output remains complete when default routine fields are absent from the blueprint.

Definition of done:

- Lesson plans, slide decks, discussions, quizzes, study guides, assignments, and custom families still compile from the leaner lesson atoms.
- Compiler output keeps teachability without bloating blueprint storage.
- The compiler preparation path now rebuilds missing workload, Bloom inference, difficulty, class-session, misconception, model-contrast, readiness, prerequisite, feedback, transfer, accessibility, teaching-intent, modality, and artifact-genre routine fields before compilation.

### Phase 5: Deterministic Repair Library

Goal: finalizer repairs structural and wording problems before spending provider calls.

Implementation slices:

1. Add deterministic repair recipes for missing lesson coverage, FAQ category gaps, quiz point totals, rubric alignment, scoring math, weak receipts, stale lesson titles, stale artifact names, and placeholder language.
2. Mark each repair in the proof bundle.
3. Use model retry only when the repair requires source-grounded semantic interpretation.
4. Add tests for repair-before-model behavior.

Definition of done:

- Finalizer can repair common package issues with zero provider calls.
- Receipts show what was fixed, skipped, failed, and why.

### Phase 6: Stale Regeneration From Semantic Blueprint

Goal: when course-map or blueprint atoms change, regenerate affected compiled deliverables deterministically.

Implementation slices:

1. Map course-map field changes to affected compiler outputs.
2. Rebuild only affected compiled deliverables from the semantic blueprint.
3. Add state-diff receipts showing before/after, affected deliverables, skipped items, and verification.
4. Keep model edits for unsupported custom/model-generated artifacts only.

Definition of done:

- A lesson title/objective/artifact edit updates stale compiled outputs without a provider call.
- The agent can explain exactly which deliverables changed and why.

### Phase 7: Audit And Release Gate Migration

Status: compiler-unit gate implemented in v0.8.4; deep audit matrix migration remains the next release-operability hardening step.

Goal: update proof gates to judge the new architecture correctly.

Implementation slices:

1. Update `audit:gold` to check `BlueprintSemanticContract` for source truth and `CompilerOutputContract` for package proof.
2. Stop treating absence of blueprint-stored report surfaces as a blueprint maturity failure.
3. Add a new matrix that reports blueprint size/derived-output split.
4. Keep export proof-language guards.
5. Keep missing-deliverable refusal tests.

Definition of done:

- Audits prove both sides of the split:
  - semantic blueprint is source-faithful and safe
  - compiler output is complete, teachable, coherent, export-safe, and reviewable
- Focused compiler coverage now includes a lean-restored blueprint test and 10 prompt-style/lesson-scope scenarios that validate the compiler-output contract.

## Success Metrics

v0.8.4 should improve:

- Provider-call savings for custom and regeneration paths.
- Number of outputs compiled from no-key restored workspaces.
- Percentage of package trust evidence generated by compiler/finalizer instead of stored blueprint bulk.
- Closed-loop stale-regeneration pass rate.
- Missing-deliverable refusal coverage.
- Export proof-language cleanliness.
- Audit clarity: source-truth failures and compiler-output failures are reported separately.
