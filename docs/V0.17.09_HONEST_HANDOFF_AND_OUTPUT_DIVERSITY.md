# V0.17.09 Auditable Evidence and Output Diversity

## Goal

Make a generated package honest about what passed, what still needs review, and which evidence actually came from the authoring run, while reducing the visible repetition created when many deliverables consume one thin model response.

## Observed failure

A live v0.17.08 Python-for-public-policy package was complete at the file level but not trustworthy as a classroom-ready result. It contained all nine deliverable families and passed ZIP integrity, yet the quality report found a P1 issue, 22 warnings, 85 reconstructed fields, repeated one dominant phrase 43 times, and attached unrelated or exporter-created sources. The interface still described the package as ready. Five explicit lessons were parsed inconsistently, and the requested notebook and dataset workflow was absent.

The Roundtable review reached the same architectural conclusion from the code: the small browser model is a constraint, but it is not the whole cause. The pipeline amplified one thin semantic kernel across nine surfaces, repaired missing fields without a strong handoff disclosure, mixed file integrity with content approval, and allowed the exporter to make provenance look richer than the run really was.

## Lane 1 — One auditable handoff vocabulary

- `finishStatus` remains the operational download state: `ready` or `blocked`.
- `trustState` is the human claim: `clean`, `review`, `not-graded`, or `blocked`.
- `exportVerification.status` reports whether package files are valid; `contentDisposition` separately reports `publishable`, `needs-review`, or `blocked`.
- Versioned warning and blocker domain ledgers travel through the run digest and package manifest.
- Readiness and export check identities are not truncated, so the receiving reviewer can reconstruct every non-passed gate.

## Lane 2 — Provenance cannot improve during export

- The exporter no longer creates generic UX, Python, music, or literature source graphs.
- Course identity is bound before ledger admission so a graph that omitted its own title cannot bypass course-aware source checks.
- A thin source ledger remains thin and review-required. The ZIP may describe that limitation, but it may not invent rows to conceal it.

## Lane 3 — Review findings remain review findings

- P0 findings block publication.
- P1 and P2 findings enter the readiness warning channel and cap the professor-adoption verdict below classroom-ready.
- Deterministically reconstructed CurriculumV1 fields are counted in generation provenance and disclosed in readiness and quality reports.
- The interface uses “exportable with review notes” when download is safe but content review remains.

## Lane 4 — The requested course contract survives compilation

- “This exact five-lesson sequence” and other hyphenated count forms recover the explicit lesson count.
- A Python data-analysis workflow requires a dataset, data dictionary, notebook, and script, rather than treating generic documents as a complete lab.

## Lane 5 — Every quality point is auditable

- “Automated readiness” is replaced by “deterministic package evidence.” Its potential is always 100 points, divided into earned, lost, and unobserved; deleting evidence cannot shrink the ruler or promote the result.
- Each versioned rule records its construct, observed evidence, exact predicate, recoverability, evidence tier, confidence basis, point buckets, causal improvement action, dependencies, and anti-gaming controls.
- Missing ordered curriculum evidence is author-recoverable and unobserved. Extraction-only source receipts and broad conformance scores cannot masquerade as semantic grounding or assessment coherence.
- Deep-grader deductions have stable rule identities and exact point effects. P0 and P1 aggregate caps are serialized as replayable `before → cap → after` transforms.
- `SCORE_LEDGER.json` carries both scoring constructs, is SHA-256 linked from the manifest, and binds the sorted byte inventory that the grader actually read, including the manifest before its quality block was added.
- Hydration distinguishes `verified`, `stale-regrade-required`, `invalid`, and `unverifiable-legacy`. Handoff logic no longer parses report prose, and trust policy no longer uses an unexplained aggregate score threshold.

## Lane 6 — Diversity comes from admitted evidence, not cosmetic paraphrase

- Native completion keeps authored terms and verified quiz projections before filling missing terminology from exact admitted fact subjects.
- When several admitted facts exist, deliverable families start from different fact and term positions.
- Definitions remain exact admitted facts; the compiler changes routing and instructional framing rather than inventing new claims.
- Short title finalization keeps a compact complement when a strict crop would end on a connector.

## Verification

- Focused regressions cover the exact production prompt, required Python assets, P1/P2 review handling, reconstructed-field disclosure, trust serialization, export/content separation, source non-invention, fixed-potential scoring, score replay and tamper rejection, quiz-priority preservation, cross-family fact diversity, and title completion.
- The normal unit, lint, format, build, bundle, browser-runtime, release-history, CI, deployment, and live production audits remain mandatory.
- A post-deployment same-prompt ZIP audit is evidence about this release only after the production footer reports v0.17.09.

## Release Boundary

V0.17.09 fixes known architectural amplification and handoff-truth failures. It does not claim that a small local Gemma model now produces expert curriculum unaided, that all warnings are automatically repairable, or that external instructors approved the result. The release is a checkpoint only if a fresh production package materially improves repetition, provenance, requested-asset coverage, disclosure, and formatting without regressing file integrity.
