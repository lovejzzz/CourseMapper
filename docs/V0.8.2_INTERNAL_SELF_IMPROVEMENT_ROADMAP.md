# CourseMapper v0.8.2 Roadmap: Internal Self-Improvement Release

Date drafted: 2026-06-04
Source audit: `docs/WEBSITE_DEEP_AUDIT_2026-06-04.md`
Version target: `0.8.2`

## Release Thesis

v0.8.2 should remove external expert audit as a release dependency and replace it with a stricter internal self-improvement loop.

The product claim changes from:

> externally proven by expert reviewers

to:

> internally self-audited, regression-tested, export-verified, and continuously improved against adversarial course-quality fixtures.

That is a better fit for the current product. CourseMapper already has strong deterministic compilation, gold fixtures, package finalization, export checks, and live agent tests. v0.8.2 should harden those into a repeatable internal quality engine instead of waiting on external proof.

## Non-Negotiable Claim Boundary

Allowed 0.8.2 claims:

- Internally self-audited.
- Regression-tested across deterministic compiler, export, agent, and browser flows.
- Gold-sample quality-gated.
- Privacy and security hardened for controlled pilots.
- Ready for internal dogfooding and small controlled pilots after P0 fixes pass.

Blocked claims:

- Externally expert-certified.
- Externally proven A-quality.
- Guaranteed classroom-ready without instructor review.
- Institution-approved or policy-approved without local confirmation.

External proof tools may stay in the repo as optional research/proof collection, but they are not a 0.8.2 release gate.

## 0.8.2 Release Gates

The release is ready only when all gates below pass from a clean implementation branch.

| Gate                             | Required result                                                                                                     |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Static health                    | `npm run lint`, `npm run format:check`, and `npm run build` pass.                                                   |
| Unit health                      | `npm test` passes with no new skipped critical suites.                                                              |
| Browser health                   | `npm run test:e2e` passes.                                                                                          |
| Export and compiler health       | `npm run audit:pipeline` passes with `0` release blockers and `0` release warnings.                                 |
| Gold quality health              | `npm run audit:gold` passes with minimum quality `9`, minimum classroom excellence `10`, and `0` blockers/warnings. |
| Internal self-improvement health | New internal self-improvement audit passes with adversarial fixtures, repair checks, and regression receipts.       |
| Security health                  | Production audit stays clean, CSP/security headers exist, and known secret persistence gaps are closed.             |
| Live provider smoke              | Private API-backed smoke passes without key leakage and without exceeding the configured budget.                    |

## Stream A: Internal Self-Improvement Loop

Goal: replace external audit dependency with a deterministic, adversarial, repeatable self-improvement system.

### A1. Add an Internal Self-Improvement Audit

Create a new gate, tentatively:

```bash
npm run audit:self
```

Suggested report output:

```text
verification-output/internal-self-improvement/latest.md
verification-output/internal-self-improvement/latest.json
```

The audit should compile a curated set of hostile and messy course maps, run the package through existing validators, run additional self-critique checks, and produce a fix-priority matrix.

Acceptance:

- Audit produces a stable Markdown and JSON report.
- Report separates blockers, warnings, improvement candidates, and accepted risks.
- Audit fails on classroom-facing genericness, source-fidelity loss, impossible timing, hidden assumptions, export leakage, or missing repair receipts.
- Audit does not require external reviewer fixtures.

First slice:

- Add the script and one adversarial fixture family with tests proving the report fails on at least one intentionally bad package and passes on one known-good package.

### A2. Add Adversarial Course Fixtures

The current 40 gold samples are strong. v0.8.2 should add a smaller adversarial fixture set that tries to break the compiler.

Fixture families:

- Vague syllabus with missing assessments.
- Overloaded course with impossible weekly workload.
- Messy copied table with duplicate and contradictory lesson rows.
- Course with source conflicts and placeholder dates.
- Lab or clinical course with safety-sensitive assumptions.
- Online asynchronous course with no live class time.
- Humanities seminar where close reading should not become generic discussion.
- Quantitative course where problem-solving evidence should not become essay evidence.
- World-language course where communicative practice should not become generic reflection.
- Custom deliverable request that must stay model-generated with an explicit receipt.

Acceptance:

- Each adversarial fixture has expected review flags.
- The compiler either repairs safely or marks local review clearly.
- Student-facing exports stay clean.
- `audit:gold` or `audit:self` fails if a fixture silently smooths over a source risk.

First slice:

- Add `sparse-official-dates-and-assessments` and `contradictory-clinical-schedule` fixtures.

### A3. Make Self-Critique Checks More Instructional

Add internal checks that attack the quality of the package, not just structure.

Checks:

- Objectives map to practice, assessment, rubric, quiz/check, feedback, and revision.
- Lesson timing is plausible for live and out-of-class workload.
- Rubrics measure the named construct rather than polish.
- Feedback loops happen before final judgment.
- Activities match modality and learner role.
- Accessibility and participation supports are concrete.
- Source-grounding and local-review boundaries are visible to instructors.
- Internal compiler/proof language never leaks to students.
- Repeated surface copy is blocked in classroom-facing materials.

Acceptance:

- Each check has at least one positive and one negative fixture.
- Findings include the lesson, artifact, and violated invariant.
- The report names the narrowest suggested repair path.

First slice:

- Add a timing/workload plausibility check because this is easy to explain to users and hard for generic output to fake.

### A4. Add Self-Improvement Receipts

Every package should expose a compact internal receipt that can be rendered in the UI and stored in audit output.

Receipt fields:

- compiled deliverables count
- model-generated deliverables count
- deterministic repairs count
- review-required lessons count
- source-grounded lessons count
- inferred assumptions count
- export formats verified
- student-facing cleanliness status
- local confirmation checklist
- live provider call count and budget status

Acceptance:

- Receipt appears in the package handoff surface.
- Receipt appears in agent responses.
- Receipt is available in audit reports.
- Receipt is included in tests so regressions are visible.

First slice:

- Add a compact trust-summary helper that reuses existing package trust evidence instead of duplicating logic.

### A5. Keep `audit:expert` Internal, Demote External Gates

Do not delete the existing expert-review scripts. Reframe them.

0.8.2 behavior:

- `npm run audit:expert` remains an internal provisional quality harness.
- `npm run audit:expert:packet`, `audit:expert:preflight`, and `audit:expert:external` remain optional proof-collection tools.
- No 0.8.2 release checklist should require external fixtures.
- Docs should state that external proof is optional and separate from internal self-improvement readiness.

Acceptance:

- Roadmap and release docs no longer block v0.8.2 on external proof.
- External proof docs remain honest about what they prove if someone chooses to use them later.

First slice:

- Add a short "External proof is optional for v0.8.2" note to release docs after `audit:self` exists.

## Stream B: Security and Privacy Hardening

Goal: make the static BYOK web posture safer for controlled pilots.

### B1. Add Hosting Security Headers and CSP

Add Firebase Hosting headers or equivalent deploy-time headers.

Required policies:

- `Content-Security-Policy`
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy`
- `Permissions-Policy`
- `frame-ancestors` protection

Acceptance:

- Local or built output has documented expected headers.
- CSP permits only the required provider/API/CDN surfaces.
- Tests or docs catch accidental removal.

First slice:

- Add a Firebase Hosting header configuration and a small verification script or test that asserts the configured header names.

### B2. Decide Runtime CDN Strategy

Current runtime imports use jsDelivr for KaTeX, Mermaid, and html2canvas. That is workable, but it should be deliberate.

Options:

- Self-host these assets through the build.
- Keep CDN loading with strict CSP and pinned versions.
- Hybrid: self-host KaTeX and Mermaid, keep html2canvas lazy if size pressure matters.

Acceptance:

- The chosen strategy is documented.
- CSP and runtime loading match the strategy.
- Browser/e2e still passes diagram/math rendering paths.

First slice:

- Document the strategy and add a regression test for the configured URLs or bundled asset paths.

### B3. Harden HTML Insertion and Chat Secret Redaction

Fix two trust gaps from the audit.

Work:

- Sanitize or tightly constrain KaTeX-rendered HTML before `dangerouslySetInnerHTML`.
- Extend chat message persistence sanitization to redact key-like values inside arbitrary message strings, not only secret-like object fields.

Acceptance:

- Tests prove pasted API-key-like text is redacted before local chat persistence.
- Tests prove allowed math still renders.
- Tests prove malicious math/link payloads do not survive into rendered HTML.

First slice:

- Reuse the stronger snapshot sanitizer's value-pattern logic for chat persistence.

### B4. Resolve `server.js`

The static app story is good. The dormant Express proxy is not production-ready.

Decision:

- Remove/archive it if it is not part of deployment.
- Or harden it before any deployment: strict CORS, stable secret handling, CSRF/rate limits, smaller body limits, no session-stored provider keys without an explicit security model.

Acceptance:

- README and deployment docs no longer leave ambiguity about whether `server.js` is production-supported.
- If retained, it has tests or a hard "development only" guard.

First slice:

- Add a clear development-only banner and deployment warning, then decide whether a removal PR is appropriate.

## Stream C: First-Run UX Simplification

Goal: make the main course-generation path feel like a finished product instead of an expert configuration console.

### C1. Keep Primary CTAs Visible

Observed problem:

- Feature-selection CTA was below the fold at 1280 x 720.
- Configuration CTA was far below the fold at 1280 x 720.

Acceptance:

- Main CTA is visible or sticky on landing, feature selection, and configure screens at common desktop and mobile viewports.
- Playwright screenshot or locator tests cover 1280 x 720 and a mobile viewport.

First slice:

- Add a sticky action footer for feature selection and configure screens.

### C2. Make the Preview Prompt-Aware or Clearly Generic

Observed problem:

- Spanish healthcare prompt led to a machine-learning illustrative preview with `3 lessons` while selected scope was `All (8 lessons)`.

Acceptance:

- Preview reflects the current prompt/scope, or is visually separated and labeled as a generic example that cannot be mistaken for the current course.
- Scope label matches selected lesson scope.

First slice:

- Replace the static sample title/scope with prompt-derived course title and selected lesson count.

### C3. Collapse Advanced Settings by Default

The configure screen is too dense for first-run users.

Default-visible:

- course title/scope
- selected deliverables
- recommended generation mode
- primary Generate action
- compact trust note

Collapsed:

- model tuning
- institution profile details
- per-deliverable advanced options
- advanced columns

Acceptance:

- First-run path requires fewer visible decisions before Generate.
- Existing advanced settings remain reachable.
- E2E covers opening advanced controls.

First slice:

- Group institution profile and model tuning behind a single Advanced section.

## Stream D: Release Operability

Goal: make audits easier to run, interpret, and trust.

### D1. Add Progress Output to `audit:gold`

Observed problem:

- `npm run audit:gold` passed but ran for about 5 minutes with little progress output.

Acceptance:

- Audit logs current sample count, scope, and elapsed time.
- Failures print the exact fixture and quality dimension.
- CI logs are readable without opening JSON.

First slice:

- Add per-sample progress logging and elapsed-time summary.

### D2. Add Scoped Fast Modes

Keep full gates for release, but make narrow development cheaper.

Suggested modes:

```bash

npm run audit:gold -- --modality clinical-simulation
npm run audit:self -- --fixture contradictory-clinical-schedule
```

Acceptance:

- Scoped mode exercises the same validators as full mode.
- Full mode remains the release gate.
- Roadmap slices can cite narrow commands without skipping real coverage.

First slice:

- Add `--sample` and `--modality` options to `audit:gold`.

### D3. Add a Private Live Full-Generation Smoke

Current live OpenAI agent audit passed. v0.8.2 should add one bounded live full-generation smoke.

Acceptance:

- Uses the private API file pattern.
- Runs one small package and one standard package, or one package if budget is tight.
- Asserts final package readiness, export availability, clean terminal state, budget compliance, and no key leakage.
- Is not required for public CI.

First slice:

- Add a documented manual command and one small fixture before automating it.

## Stream F: Trust Surface in the App

Goal: users should see why the package is trustworthy without reading audit reports.

### F1. Compact Trust Summary Card

Add a small card in the package handoff or workspace that says what happened.

Example:

```text
Compiled: 9 deliverables
Model-generated: 0 core deliverables
Repairs: 3 safe repairs
Review needed: 2 lessons
Exports verified: ZIP, DOCX, PPTX, XLSX, PDF
Local confirmations: official dates, copyrighted readings
```

Acceptance:

- Uses existing trust evidence helpers where possible.
- Does not expose internal proof jargon to students or exported classroom materials.
- Covered by component tests and at least one e2e assertion.

First slice:

- Add the compact card to the final handoff/package summary path.

### F2. Make Review-Required Rows Actionable

Users should not just see "review required." They should see what to check.

Acceptance:

- Each review-required item has action text.
- Actions distinguish official dates, source permissions, local policy, assessment weights, safety-sensitive assumptions, and missing inputs.
- Export/package readiness still permits draft handoff only when the review boundary is visible.

First slice:

- Surface the existing local-review action fields more prominently in the package summary.

## 0.8.2 Done Definition

v0.8.2 is done when:

- External expert audit is no longer listed as a release blocker.
- Internal self-improvement audit exists and passes.
- Security P0s from the website audit are closed or explicitly documented with accepted-risk reasoning.
- First-run CTA and preview issues are fixed.
- `audit:gold` is observable enough that a 5-minute run does not look hung.
- Full verification passes:

```bash
npm run lint
npm run format:check
npm run build
npm test
npm run test:e2e
npm run test:rules
npm run bundle:check
npm run audit:pipeline
npm run audit:gold
npm run audit:expert
npm run audit:self
```

- Private live provider smoke passes when API keys are available.
- Release notes use the honest claim boundary: internally self-audited, not externally certified.

## Out of Scope for 0.8.2

- Public external expert certification.
- Major React/Tailwind/pdfjs migrations unless required by a blocker.
- A production backend key vault.
- New broad feature families unrelated to reliability, trust, UX, security, or self-improvement.
- Claiming that users no longer need local instructor review.
