# V0.15.18 - CourseIR Repair Boundary

## Goal

v0.15.17 let large-output models author one dense CourseIR object before the
compiler. The next quality risk is accepting a provider CourseIR only because
the deterministic repair layer fixed it afterward.

v0.15.18 separates those responsibilities:

1. Direct provider authoring must return a CourseIR brain that is already dense
   enough to pass direct-authoring acceptance.
2. Compiler repair still runs before rendering for explicit CourseIR inputs.
3. Repaired structure is visible as fallback evidence, not hidden as accepted
   direct authoring.

## Lane

This is a narrow CourseIR acceptance-boundary slice. It does not change the
provider prompt, the native skeleton path, or the deterministic compiler
surface. It changes the proof rule for direct provider authoring: repaired
structure is a valid compiler safety net, but it is not evidence that the model
authored a complete CourseIR brain.

## Boundary

The same malformed CourseIR can have two different outcomes depending on where
it enters:

1. **Provider direct authoring path:** rejected as direct authoring when repair
   was required. The app falls through to native skeleton/prose fallback and
   records the repair reason.
2. **Compiler CourseIR path:** repaired before DOCX/PPTX rendering, then
   compiled deterministically with proof metadata such as
   `repairedBeforeCompile`.

That distinction matters because the long-term goal is not just "valid JSON."
It is a model-authored curriculum brain with real concepts, outcomes,
assessment coverage, worked examples, misconceptions, sources, constraints,
and prerequisite links.

## Release Boundary

v0.15.18 ships only after focused CourseIR regression coverage, formatting,
lint, build, bundle check, full unit suite, constitution audit, and
release-history audit. Remote Fast verification and Pages deploy are claimed
only after push.

## Acceptance

This slice is acceptable when:

1. `parseCourseIRResponse` reports `repairedBeforeAcceptance` when structural
   repair was needed.
2. Direct CourseIR acceptance rejects repaired provider structures.
3. The compiler still repairs under-assessed CourseIR before deterministic
   rendering.
4. Focused CourseIR tests prove both sides of the boundary.

## Carry Forward

The remaining work is to make this fallback rarer rather than merely honest:
provider prompts need stronger per-lesson assessment/rubric requirements,
larger domain genome coverage should reduce assumption repair, and live
EduTool.dev ZIP/log audits should compare direct accepted CourseIR against the
native skeleton path on the same briefs.
