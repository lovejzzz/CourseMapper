# V0.15.5 — The Truth Ledger: the changelog becomes a contract

_Written June 14, 2026, from `docs/CHANGELOG_TRUTH_AUDIT_2026-06-14.md`.
Theme: CourseMapper has enough feature history. The next release must make its
history auditable, generated from one release source, and honest about what is
current, historical, superseded, local-only, CI-proven, or waiting for humans._

## Goal

Make every release claim traceable. A maintainer should be able to answer:
what shipped, which code owns it, which command proved it, whether the proof is
current, and which planned work was carried forward instead of silently implied.

## Lane 1 — Current Release Manifest

1. Add a tiny current-release manifest that owns the current version, release
   date, title, landing summary, changelog highlights, and proof pointers.
2. Derive `APP_VERSION`, the landing "What's new" popover, and the top changelog
   entry from that manifest.
3. Remove hard-coded footer version labels from Landing/Configure/Feature Select
   and Workspace surfaces.

**Bar:** `npm run audit:release-history` fails if package version,
`APP_VERSION`, latest release, top changelog entry, package-lock, or footer
surfaces drift.

## Lane 2 — Release Contract Ledger

1. Add `release-contracts/v0.15.5.json` for the current release and preserve
   `release-contracts/v0.15.4.json` as the archived truthfulness contract.
2. Require each current-release claim to name code anchors and proof commands.
3. Mark each claim status as `verified-current`, `historical`, `superseded`,
   `manual-only`, or `carry-forward`.

**Bar:** the release-history audit fails if a current release has no contract,
if any claim has no proof command, or if any claim has no code/doc anchor.

## Lane 3 — Roadmap Truth

1. Mark `docs/V0.15.4_MOVING_THE_MEANS_ROADMAP.md` as superseded/carry-forward.
2. Keep `docs/V0.15.4_TRUTHFUL_LINEAR_ALGEBRA_ROADMAP.md` as the shipped v0.15.4
   plan.
3. Put the remaining "Moving the Means" lanes into future work explicitly:
   depth tier 2, mandarin mean movement, `useDeliverables` split, instructor
   verdict, and thin-shard deepening.

**Bar:** the release-history audit fails if a superseded roadmap is missing a
status note.

## Lane 4 — Comment Truth

1. Fix stale comments that still describe native authoring as prose-default.
2. Fix stale comments that still describe the voice pass as default-off.
3. Fix Crucible comments where omitted `--authoring` is named "prose" even
   though the plain round intentionally tests native/voiced app defaults.

**Bar:** the release-history audit scans the known drift files and fails on the
old phrases.

## Lane 5 — Remote Proof Ritual

Fast CI is required on every push and Pages deploy follows it. Deep proof is
heavier and intentionally not every `main` push. That distinction must be
visible in release work.

1. Document that compiler/grader releases need either a `release/**` branch or
   a manual deep-proof dispatch before a remote proof claim.
2. Keep local `audit:gold` and browser smoke as local proof, not a substitute
   for claiming remote deep proof.
3. Add release-contract fields that distinguish `local`, `ci-fast`, `ci-deep`,
   `live-provider`, and `manual-human` proof.

**Bar:** a release cannot claim remote deep proof unless the contract records a
deep-proof run or explicitly says it is pending/not applicable.

## Lane 6 — Future Vision, Not This Patch

These are the ambitious next moves, deliberately scoped beyond the immediate
truth-ledger patch:

1. **Human ruler:** convert `docs/instructor-review/` into a real feedback
   ingestion loop with margin notes, cause classification, and follow-up
   roadmap generation.
2. **CurriculumOS lift-out:** route app compile/link/grade paths through
   `src/curriculumos`, then prepare the engine as a CLI/package/API boundary.
3. **Provenance inspector:** let instructors inspect why each exported artifact
   exists, which source/kernels support it, and what still needs local review.
4. **Mean movement:** restart the carried v0.15.4 "Moving the Means" lanes only
   when the release contract can show judge/human movement, not just new code.

## Release Boundary

v0.15.5 should not inflate the product surface. It should make the existing
product more trustworthy by turning release history into enforceable metadata,
tests, and scripts. Anything that changes generated course quality belongs in a
separate compiler/grader release with full proof.
