# V0.15.10 - CourseIR Architecture: one canonical course brain before compilation

_Written June 19, 2026. This roadmap follows the provider-call rightsizing work
in v0.15.9 and captures the next strategic reduction: stop asking the provider
to rewrite the same course into many final artifacts._

## Goal

Build the next generation path around a dense `CourseIR` source of truth. The
model should produce one validated, machine-readable representation of the
course, and CourseMapper should compile every final package artifact from that
representation.

The target is not one giant final-prose response. The target is one canonical
course brain that is compact for the provider, stable for the compiler, and
auditable by the local grader.

## v0.15.10 Shipped Slice

v0.15.10 ships the first narrow vertical slice of this architecture:

- `CourseIR v1` normalization and validation, including source-ledger,
  lesson/concept/assessment coverage, repair paths, and coverage ledger stats.
- A model-capacity planner that decides whole-course IR, lesson-block IR,
  global-plus-block IR, or fallback to the current generation path from actual
  context/output limits.
- A dense structured-output prompt contract that asks providers for semantic
  atoms instead of final artifact prose.
- A deterministic compiler adapter that converts CourseIR into the existing
  CourseGraph/blueprint compiler path and records zero provider calls during
  compilation.
- A CurriculumOS facade entry point: `compileCourse({ courseIR })`, plus
  CourseIR-aware proof metadata that can ride into package manifests through
  `gradePackage`.
- Unit proof around validation, projection, deterministic artifact compilation,
  legacy course-map normalization, capacity planning, and manifest handoff.

This is still flag-ready infrastructure, not a default product flip. The
default path should move only after side-by-side 5-, 8-, and 15-lesson package
proof shows equal or better quality with lower call count or token cost.

## Reason

The current pipeline has already reduced avoidable calls, but it still asks
multiple model passes to reason over overlapping course context. That creates
four costs:

- Cost: repeated prompts pay again for context the app already knows.
- Drift: lesson plans, slides, quizzes, and reports can slowly disagree when
  they are enriched or polished through separate passes.
- Retry waste: a later artifact-specific miss often triggers a provider call
  even when the missing fact should have been part of the central course model.
- Audit opacity: the final ZIP may be structurally complete while the source of
  a factual choice or compiler assumption is scattered across logs and
  deliverables.

`CourseIR` should make the model decide the educational structure once. The
compiler should do the repetitive rendering work.

## Design Decision

CourseMapper should prefer this flow:

1. Normalize the user's course input into a compact source packet.
2. Ask the selected model for `CourseIR`, not final package prose.
3. Validate `CourseIR` against a strict schema and course-coverage rules.
4. Repair only invalid or missing IR paths.
5. Compile final artifacts deterministically from the validated IR.
6. Grade the ZIP against the IR, manifest, digest, and exported files.

This keeps provider output dense without making it cryptic. The IR should use
JSON, stable IDs, arrays, enums, and short structured fields. It should not use
an invented compression language that future models or compilers must guess.

## CourseIR v1 Shape

The first schema should include these sections:

| Section           | Purpose                                                                                         |
| ----------------- | ----------------------------------------------------------------------------------------------- |
| `course`          | title, discipline, level, modality, duration, audience, source provenance                       |
| `sourceLedger`    | what came directly from user input, what is standard domain knowledge, what is an assumption    |
| `concepts`        | stable concept IDs, prerequisite edges, misconceptions, factual anchors, vocabulary             |
| `lessons`         | lesson kernels, objectives, concepts, prerequisite checks, worked-example specs, practice specs |
| `assessments`     | assessment atoms, coverage links, weight/provenance notes, rubric dimensions                    |
| `artifactIntents` | what each deliverable must include, referenced by IDs instead of copied prose                   |
| `handoffNotes`    | instructor review flags, local confirmation needs, caveats that must surface in reports         |
| `qualityHints`    | expected risks for the grader to verify rather than trust                                       |

Example kernel shape:

```json
{
  "id": "L03",
  "topic": "Limit laws",
  "conceptIds": ["C07", "C08"],
  "objectives": ["apply sum, product, and quotient limit laws", "identify when direct substitution is not valid"],
  "workedExamples": [
    {
      "id": "E03A",
      "skill": "evaluate polynomial limits",
      "setup": "lim x->2 of x^2 + 3x",
      "solutionSteps": ["substitute x=2", "compute 4+6", "answer 10"]
    }
  ],
  "misconceptions": [
    {
      "claim": "Students may apply the quotient law before checking the denominator.",
      "correction": "Check the denominator and domain before using quotient-law substitution."
    }
  ]
}
```

## Lane 1 - Schema and Capacity Planner

Add a `CourseIR v1` schema with strict required fields, stable IDs, and bounded
field lengths. Add a model-capacity planner that estimates:

- source input tokens
- expected IR output tokens
- provider context window
- provider output cap
- structured-output reliability reserve
- cost by input and output token
- repair risk for large outputs

The planner should choose:

- one whole-course IR call when the course fits with reserve
- the fewest lesson-block IR calls when output cap is the bottleneck
- global graph first, then block-level IR, when the course is too large for one
  reliable output
- the current batching path as fallback for models without reliable structured
  output

## Lane 2 - Dense Prompt Contract

The prompt should ask for semantic atoms, not polished files. It should request
compact but complete educational structure:

- factual anchors
- misconception correctives
- worked-example specifications
- assessment blueprints
- prerequisite links
- lesson-to-concept coverage
- instructor caveats
- source/assumption tags

The prompt should forbid final prose expansion except in short fields where the
compiler needs exact wording. This is what reduces cost without lowering
quality.

## Lane 3 - Deterministic Compiler Adapter

Add compiler adapters that render existing package artifacts from `CourseIR`.
The adapters should reuse the current deliverable compiler where possible, but
their contract should be stricter:

- no hidden provider calls during deterministic compilation
- every rendered section traces back to an IR ID
- every assessment in the course map has an artifact implementation or an
  explicit handoff note
- every final file can be checked against the IR coverage ledger

The package should be able to explain itself: `PACKAGE_MANIFEST.json`,
`QUALITY_REPORT.md`, and the run digest should identify the IR version and
which artifacts were compiled from it.

## Lane 4 - Validation and Targeted Repair

Validation should run before export and after ZIP assembly:

- JSON schema validity
- unique and resolvable IDs
- lesson count parity
- assessment coverage parity
- concept graph connectivity
- source-ledger completeness
- minimum worked-example and practice density
- no orphan artifact intents
- no missing handoff notes for assumptions

Repair calls should be path-scoped. If `lessons[6].workedExamples` is thin,
repair that path. Do not regenerate the whole course unless the global graph is
corrupt.

## Lane 5 - Proof Ladder

Ship the implementation behind a flag. Compare CourseIR against the current
pipeline on the same prompts and providers:

| Scope      | Evidence                                                |
| ---------- | ------------------------------------------------------- |
| 5 lessons  | small-course overhead does not get worse                |
| 8 lessons  | mid-size package keeps assessment and artifact coverage |
| 15 lessons | full-course path proves the cost and drift reduction    |

Each proof run should record:

- provider call count
- estimated and actual cost
- output token use
- retry count and repair paths
- local deep-grader score and P0/P1/P2 findings
- digest caveats
- manifest/export completeness
- artifact parity against the IR
- human-visible texture risks

The flag should not become default until CourseIR is at least as good as the
current path on package completeness and deep-grade findings, while using fewer
provider calls or lower total token cost.

## Monster Compiler Requirement

For this architecture to work, CourseMapper needs a much stronger compiler than
a template expander. The provider call becomes the author of the course's
semantic source, but the compiler becomes the teacher, editor, auditor, and
publisher. That is the only way one dense call can create better materials
instead of just cheaper materials.

The compiler needs these subsystems:

| Subsystem             | Job                                                                                                                                           |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| IR normalizer         | Accept CourseIR, legacy CourseGraph, and current course maps behind one internal shape                                                        |
| Schema validator      | Reject malformed IDs, missing lesson atoms, invalid assessment links, and unsafe assumptions                                                  |
| Graph linker          | Resolve lesson concepts, prerequisite edges, repeated concepts, review lessons, and cross-lesson dependencies                                 |
| Genome linker         | Attach Curriculum Genome kernels, citations, misconception inventories, vocabulary, and source tiers where available                          |
| Lesson planner        | Turn lesson kernels into teachable sequences with warm-ups, instruction moves, checks for understanding, practice, and closure                |
| Assessment reconciler | Ensure every course-map assessment has a typed artifact, coverage links, answer key or rubric, and handoff note                               |
| Artifact planner      | Decide what each final material needs from the IR without copying prose between artifacts                                                     |
| Renderer adapters     | Compile syllabus, lesson plans, slides, assignments, rubrics, discussions, quiz bank, study guides, FAQ, manifest, and reports                |
| Provenance ledger     | Track whether each substantive claim is source-provided, genome-cited, standard domain knowledge, model-authored, or instructor-review-needed |
| Texture engine        | Vary opener patterns, examples, practice shapes, slide rhythms, and review language without breaking traceability                             |
| Repair orchestrator   | Retry only invalid IR paths or failed compiled surfaces, never blind-regenerate the whole course by default                                   |
| Export verifier       | Check the ZIP, manifest, quality report, digest, file count, assessment parity, and artifact readability before download                      |
| Sync engine           | Propagate approved course-map edits back through IR and affected artifacts without losing local instructor edits                              |
| Quality grader        | Grade the final package against both classroom-quality heuristics and the CourseIR contract that produced it                                  |

The compiler should feel large internally, but it should expose a small public
surface. The right shape is still the CurriculumOS facade: `compileCourse`,
`linkGenome`, `extractOnMiss`, and `gradePackage`. CourseIR should strengthen
those verbs, not create a second product path.

## Quality Bar: Better Than Before

CourseIR does not automatically guarantee better quality. It can only guarantee
a better quality path if the compiler enforces stricter invariants than the
current multi-pass pipeline.

The default flip bar should be:

- no missing lessons, assessments, or selected artifacts
- no cross-artifact drift: slides, lesson plans, quizzes, rubrics, and study
  guides trace to the same lesson and concept IDs
- more factual density per lesson than the current path, measured by factual
  anchors, worked examples, misconception correctives, and assessment coverage
- fewer provider calls or lower total token cost at equal or better deep-grade
  result
- no new P0/P1 findings in local deep-grade output
- digest caveats are equal or better than the current pipeline
- teacher-facing prose remains readable after deterministic rendering
- every local-review caveat is visible in the quality report or handoff notes

The important guarantee is not "one call is smarter." The guarantee is "one
source of truth plus a stricter compiler leaves fewer places for drift to
hide." If a CourseIR package cannot beat the current path on the same 5-, 8-,
and 15-lesson prompts, the flag stays off.

## CurriculumOS V1 Improvement Vision

CourseIR should become the private course-specific layer of CurriculumOS V1.
The Curriculum Genome remains the reusable cited knowledge layer. The compiler
links them:

```text
user course input
  -> CourseIR source packet
  -> CurriculumOS linkGenome
  -> CourseIR validation and repair
  -> CurriculumOS compileCourse
  -> CurriculumOS gradePackage
  -> optional extractOnMiss for generic, privacy-stripped genome candidates
```

This improves CurriculumOS V1 in five ways:

1. **Cleaner boundary.** `compileCourse` should eventually accept CourseIR
   directly, not only a course map plus enrichment overlay. The website becomes
   a client of CourseIR-backed CurriculumOS.
2. **Stronger linker.** `linkGenome` should run as a contract verifier: every
   lesson concept is either genome-linked, source-provided, standard domain
   knowledge, or explicitly marked as model-authored and review-needed.
3. **Better deterministic floor.** When the provider misses a field, the
   compiler can still render a complete structural artifact from CourseIR and
   flag exactly what is thin. It should not silently invent missing substance.
4. **Self-improving loop.** `extractOnMiss` should learn from CourseIR misses by
   proposing generic kernel candidates only after privacy stripping, source
   checking, and instructor opt-in.
5. **Headless proof.** `gradePackage` should grade the exported package against
   CourseIR, not just against generic artifact heuristics. That gives
   CurriculumOS a stronger API-level proof than browser inspection alone.

The long-term CurriculumOS V1 contract should be:

- CourseIR is the course-specific semantic state.
- Curriculum Genome is the reusable verified knowledge state.
- The compiler is the deterministic inference engine.
- The grader is the honesty engine.
- EduTool.dev is one client, not the architecture boundary.

That is the "monster compiler" worth building: not a giant file, but a compact
public engine with many hard internal checks.

## Anti-Patterns

Do not build these:

- one huge response containing every final lesson plan, slide, quiz, rubric, and
  report as prose
- custom compression tokens that only one prompt explains
- an IR that is so terse the compiler must infer missing pedagogy
- a compiler that silently fabricates missing assessments or examples
- a green score that ignores IR validation caveats

## Release Boundary

v0.15.10 implements the first CourseIR vertical slice: schema/normalization,
validation and repair paths, capacity planning, dense prompt contract,
deterministic compilation through the existing CourseGraph/blueprint compiler,
CurriculumOS facade routing, and proof metadata for package manifests.

It does not claim that EduTool.dev defaults to CourseIR generation yet. The
feature remains behind the next flagged generation path until live side-by-side
proof beats or matches the current path on package completeness, deep-grade
findings, digest caveats, teacher-facing texture, call count, and cost.
