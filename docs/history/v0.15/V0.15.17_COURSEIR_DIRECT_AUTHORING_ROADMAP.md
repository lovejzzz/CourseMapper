# V0.15.17 - CourseIR Direct Authoring

## Goal

v0.15.16 made healthy native plans compile from a validated CurriculumV1
projection, but provider authoring still started with a native skeleton plus
Pass B enrichment. That was better than prose fallback, but it was not yet the
"one course brain first" architecture.

v0.15.17 adds the first runtime provider path where a model can author one dense
CourseIR object directly and the deliverables stage compiles from that object
without native Pass B. The path is model-capacity-gated and acceptance-gated:
it runs only when the planner says a whole-course IR response can fit, and it
ships only when the returned CourseIR proves lesson-by-lesson curriculum
coverage.

## Lane

This is a direct CourseIR runtime seam, not a blind default that forces every
model into one giant response.

In scope:

1. Try direct CourseIR authoring before native skeleton authoring when native
   mode is active, the run is full-course, the generation plan is not degraded,
   and the selected model has enough context/output capacity.
2. Reject thin CourseIR even if structural validation passes. Every accepted
   direct CourseIR must cover lessons with concepts, assessments, factual
   anchors, worked examples, constraints, and misconception correctives.
3. Hand accepted CourseIR across generation and deliverables as a single-run,
   course-keyed source object.
4. Compile accepted direct CourseIR through CurriculumV1 projection without
   native Pass B provider calls.
5. Disclose direct CourseIR proof in run events and package manifests.

Out of scope:

1. No forced one-call path for small-output or degraded models.
2. No claim that edited maps regenerate a fresh CourseIR object yet.
3. No live EduTool.dev ZIP/log quality claim for this release.
4. No broad genome shard expansion.

## Why This Should Improve Quality

Genome-linked content remains important because it gives the compiler a cited
knowledge spine where the library has coverage. It is not sufficient by itself:
genome coverage can be partial, and non-genome course structure still needs
explicit concepts, outcomes, assessments, constraints, examples, and handoff
notes.

Direct CourseIR improves the architecture when it succeeds because the model
decides the curriculum structure once, in one schema, before the compiler
renders artifacts. The compiler then expands validated atoms instead of
recovering structure from prose cells. That reduces drift between lessons,
assessments, examples, and package surfaces.

The acceptance gate is the quality brake. A giant call that returns shallow
JSON is not better curriculum intelligence; it is just a larger fallback risk.
This release lets dense CourseIR win and makes thin CourseIR fall back loudly.

## Release Boundary

v0.15.17 ships only after focused CourseIR/native/package tests, formatting,
lint, build, bundle check, full unit suite, constitution audit, release-history
audit, and the appropriate gold smoke/full gate pass locally. Remote Fast
verification and Pages deploy are claimed only after push.

## Acceptance

The release is acceptable when:

1. Dense direct CourseIR responses parse, validate, pass coverage acceptance,
   and compile deterministically.
2. Thin CourseIR responses are rejected before they can bypass native/prose
   fallback.
3. Accepted CourseIR stashes are single-use and keyed to the rendered course
   map, preventing stale cross-course merges.
4. Deliverables can compile from accepted direct CourseIR without native Pass B.
5. `PACKAGE_MANIFEST.json` can disclose `courseIR.directAuthoring`.

## Carry Forward

The next proof step is a live side-by-side EduTool.dev audit on models with
large enough output windows: direct CourseIR vs native skeleton/Pass B on the
same course brief, comparing cost, call count, local deep quality grade,
texture, fallback events, and exported ZIP evidence.
