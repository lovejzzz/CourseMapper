# V0.15.6 - The Self-Improving Ruler: CourseMapper audits itself until it finds the next real defect

_Written June 14, 2026, after deciding that v0.15.6 cannot depend on external
human reviewers. Theme: if no instructor is available, CourseMapper still needs
a way to get better. The answer is not to pretend internal proof is human proof.
The answer is to build an adversarial self-improvement system that generates
hard cases, reviews outputs through multiple independent lenses, mines defects,
proposes repairs, and proves whether each repair actually improves teachability
without breaking release truth._

## Recommendation

Focus v0.15.6 on autonomous quality discovery.

The project should build its own internal "faculty board": not a single LLM
judge, not a generic score, and not another broad test sweep. It should be a
repeatable loop that creates difficult course scenarios, compiles packages,
reviews them from several roles, extracts concrete defects, maps those defects
to code owners, and selects the next repair by evidence.

This does not replace a real instructor. The release contract must say that
manual-human proof is unavailable. But it gives the project a way to keep
improving without waiting for one.

## Goal

Build a self-improvement loop that can answer:

1. What package weakness did CourseMapper find by itself?
2. Which artifact, lesson, and generated phrase proves the weakness?
3. Which failure class does it belong to?
4. Which code owner probably caused it?
5. What repair would improve it?
6. Did the repair improve the same scenario and avoid regressions elsewhere?

The output of v0.15.6 should be a ranked repair ledger, not a vague audit note.

## Non-Goals

1. Do not claim real instructor approval.
2. Do not rely on one LLM judge score as the truth.
3. Do not add more product UI unless the audit loop proves the UI is the
   bottleneck.
4. Do not run unlimited expensive live-provider loops by default.
5. Do not ship a repair merely because one synthetic reviewer liked it; require
   cross-checks and regression gates.

## Lane 1 - Synthetic Faculty Board

Create a local review board with several independent reviewer roles. Each role
must produce evidence, not just a score.

Suggested roles:

1. **Working instructor:** would I teach this next week, and what would I change
   first?
2. **Student-in-room:** what would confuse, bore, overload, or undersupport
   students?
3. **Assessment designer:** does each task measure the intended construct?
4. **Source-fidelity auditor:** did the package preserve the source course
   signal, or invent unsupported structure?
5. **Accessibility and inclusion reviewer:** can varied learners participate,
   and are expectations explicit?
6. **Skeptical department chair:** what would block adoption, accreditation, or
   departmental trust?

Each reviewer must return:

- artifact and lesson references,
- quoted evidence or compact excerpts,
- severity,
- failure category,
- first recommended edit,
- whether the issue is global product behavior or local preference.

**Bar:** a review board run cannot pass with score-only feedback. Every finding
must name evidence and a proposed repair direction.

## Lane 2 - Adversarial Course Generator

Add a deterministic/adaptive scenario generator that creates hard internal
course maps without relying on outside humans.

Scenarios should cover:

1. sparse course maps with missing objectives and vague assessments,
2. multi-section courses where topics are easy to cross-contaminate,
3. quantitative courses requiring worked examples,
4. language courses requiring pronunciation, script, and cultural context,
5. clinical/studio/lab courses where modality matters,
6. seminars where discussion quality matters more than quizzes,
7. courses with conflicting or overloaded assessments,
8. courses with no readings,
9. courses with too many readings,
10. courses where local policy must be flagged rather than invented.

**Bar:** the generator writes a manifest for each scenario: why it is hard,
which failure classes it probes, and which outputs must be inspected.

## Lane 3 - Defect Taxonomy And Evidence Ledger

Create a machine-readable defect ledger for self-found issues.

Primary categories:

1. `source-compression-loss`
2. `compiler-translation-gap`
3. `artifact-pedagogy-gap`
4. `assessment-authenticity-gap`
5. `student-experience-gap`
6. `provenance-trust-gap`
7. `discipline-fit-gap`
8. `local-policy-invention`
9. `generic-template-leak`
10. `regression-risk`

Each finding should include:

- scenario id,
- package version,
- artifact,
- lesson/week,
- excerpt or structural evidence,
- reviewer role,
- severity,
- category,
- suspected owner module,
- proposed fix,
- proof command required after repair.

**Bar:** the ledger can rank defects by severity, reproducibility, affected
artifact family, and likely repair leverage.

## Lane 4 - Repair Candidate Generator

The loop should not stop at critique. For each high-value finding, generate a
repair candidate with a clear owner.

Repair candidate shape:

1. issue summary,
2. evidence excerpt,
3. suspected root cause,
4. files likely involved,
5. smallest code change that could fix it,
6. regression tests to add,
7. proof commands to rerun,
8. risk of overfitting.

**Bar:** a repair candidate is not actionable unless it names the module, the
test surface, and the anti-overfit check.

## Lane 5 - A/B Repair Proof

For any repair that touches generated output, require before/after proof.

The proof should compare:

1. original scenario output,
2. repaired scenario output,
3. synthetic faculty findings before/after,
4. deep grader findings before/after,
5. bundle/build/test impact,
6. unrelated scenario regression risk.

The system should report:

- fixed findings,
- new findings,
- unchanged findings,
- score movement by reviewer role,
- whether the repair is broad enough to keep.

**Bar:** do not ship a compiler/grader repair unless the before/after report
shows a concrete defect got better and no higher-severity defect was introduced.

## Lane 6 - No-Human Honesty In Release Contracts

v0.15.6 must be honest about proof status.

1. `manualHuman.status` should be `not-available` or `not-used`, not `success`.
2. Synthetic review should use its own proof scope, such as
   `synthetic-review`.
3. Any changelog claim must distinguish:
   - self-found defect,
   - synthetic reviewer finding,
   - deterministic audit finding,
   - live-provider proof,
   - real human proof unavailable.

**Bar:** `npm run audit:release-history` should fail if a no-human release
claims human approval or collapses synthetic review into manual-human proof.

## Lane 7 - Commands And Artifacts

Recommended command surface:

1. `npm run audit:self-improve:scenarios`
   - generate or refresh adversarial scenario manifests.
2. `npm run audit:self-improve:review`
   - compile selected scenarios and run the synthetic faculty board.
3. `npm run audit:self-improve:ledger`
   - write a ranked Markdown and JSON defect ledger.
4. `npm run audit:self-improve:repair-plan`
   - turn top findings into repair candidates.
5. `npm run audit:self-improve:proof`
   - compare before/after outputs for an implemented repair.

Recommended artifacts:

1. `verification-output/self-improvement/latest.md`
2. `verification-output/self-improvement/latest.json`
3. `verification-output/self-improvement/scenarios/*.json`
4. `verification-output/self-improvement/findings/*.json`
5. `verification-output/self-improvement/repair-candidates/*.md`

**Bar:** a maintainer should be able to open one latest report and know what
CourseMapper thinks is weakest right now.

## Lane 8 - Seeded First Run

The first v0.15.6 run should not try to cover the universe. Pick five seed
courses that probe known weak spots:

1. Linear Algebra with sparse secondary sections.
2. Beginning Mandarin with no formal reading list.
3. World Literature seminar with discussion-heavy teachability needs.
4. Clinical placement with local policy and safety boundaries.
5. Data Science lab where computational labs must not become wet labs.

**Bar:** the first ledger should produce at least one concrete repair candidate,
or explicitly say no high-confidence defect was found and why the probes were
insufficient.

## Suggested Release Claims

Only use these if implemented and proved:

1. CourseMapper now has a self-improvement audit loop that generates hard
   course scenarios, compiles packages, and reviews them through multiple
   synthetic faculty roles.
2. Self-found findings are written to a structured defect ledger with evidence,
   severity, category, suspected owner, and required proof commands.
3. The loop generates repair candidates instead of only criticism.
4. Compiler/grader repairs require before/after self-improvement proof before
   the release can claim improvement.
5. Release contracts explicitly distinguish synthetic review from unavailable
   human proof.

## Verification Plan

Local gates for the loop:

1. focused tests for scenario generation,
2. focused tests for synthetic review parsing and placeholder rejection,
3. focused tests for defect-ledger ranking,
4. focused tests for repair-candidate generation,
5. `npm run audit:self-improve:review -- --sample smoke` or equivalent,
6. `npm run audit:release-history`,
7. `npm run lint`,
8. `npm run format:check`,
9. `npm run test`,
10. `npm run build`,
11. `npm run bundle:check`.

If v0.15.6 implements an actual output repair, also run:

1. `npm run audit:self-improve:proof`,
2. `npm run audit:gold`,
3. `npm run audit:expert`,
4. `npm run test:e2e`,
5. deep proof through release branch or manual dispatch.

## The Hard Line

Without a human reviewer, the product still has to improve. But it must improve
honestly.

The right v0.15.6 claim is not:

> Instructors approve this.

The right v0.15.6 claim is:

> CourseMapper can now find, classify, rank, and prove its own next defects.

That is the self-improvement engine this project needs before the next big
product leap.
